Use this worksheet for one complete coding-problem attempt. It leaves a record of the contract you understood, the approach you chose, the tests you ran, and the next thing to practice. Print the page, copy the prompts into your notes, or use the [interview rehearsal](/tools/interview-rehearsal) to download a filled session as Markdown.

Keep the problem statement nearby. The worksheet should make your reasoning inspectable rather than become another document to complete after the learning has already happened. A short answer with a concrete example is more useful than filling every space with general advice.

## Write the contract in your own words

For [Two Sum](/course/target-two-sum), this course asks for all pairs of original indexes from unique input values. A remembered solution returning just one pair is incomplete for that contract. For [Binary Tree Maximum Depth](/course/binary-tree-max-depth), depth counts edges, so a lone root has depth zero and the empty tree has depth minus one. Write those conventions down before implementing.

Choose two clarifying questions whose answers could change the algorithm. “Can I sort the input?” matters when original positions or input preservation are required. “Are edges weighted?” matters when selecting a shortest-path strategy. A question should resolve an actual uncertainty rather than imitate interview conversation.

For a pair problem, nested loops over distinct positions are a clear baseline. For a connectivity problem, an explicit graph search may be easier to justify than immediately reaching for a specialized structure. Explain what the baseline repeats or retains. That observation supplies a reason to improve it.

Do not optimize a method that has not yet been shown to solve the task. A fast answer to a different output contract is still wrong. If the baseline depends on a precondition, such as sorted input, record that assumption rather than hiding the preprocessing cost.

A useful invariant says more than “the array is processed correctly.” For a complement map, it says exactly which positions are already stored before the current lookup. For a BFS, it distinguishes discovered vertices from processed vertices and explains when a parent is assigned.

Use the [data-structure selection reference](/reference/choosing-data-structures) when the state is clear but the representation is uncertain. Choose by required operations and order guarantees. A queue and a heap both retain candidates, but they remove them in different orders and support different correctness arguments.

A stored index zero challenges truthiness. A descendant crossing an ancestor's bound challenges a local-only BST check. A self-loop challenges graph discovery marking. Two zeros challenge product division. An input-copy comparison challenges accidental mutation. The [edge-case practice](/tools/edge-case-practice) explains these distinctions.

When possible, compare small generated inputs with an independent brute-force reference. Check the same output contract and normalize only irrelevant ordering. Keep any discovered counterexample as a regression test. Passing a few examples is evidence, not a correctness proof by itself.
