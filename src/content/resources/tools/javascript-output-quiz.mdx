## Trace bindings before evaluating expressions

For a closure, identify the binding the function reads and when it reads it. Creating an arrow that refers to count does not copy count's current value. If the same binding changes before the arrow is called, the later read sees the changed value. The two loop questions deliberately use the same callback body with different declarations. The let loop provides separate iteration bindings, while the var loop shares one function-scoped binding. The callbacks execute after the loop in both examples. Delayed execution explains the time of the reads; the declaration explains whether they read one binding or several. Neither example requires a timer.

## Separate a function from its receiver

An ordinary function's receiver depends on its invocation. Saving a method into another variable preserves the function object but does not bind it to the original owner. A property call and a detached plain call can therefore run the same body with different receiver values. Binding with bind or invoking with call changes that relationship deliberately.

An arrow uses the receiver from its surrounding lexical environment. Calling the arrow with call does not replace that captured receiver. For each example, name the ordinary function invocation that supplies this, then identify which functions inherit it. This is more reliable than treating every dot near a function as evidence of a permanent binding.

## Inspect identity, copies, and missing values

Object spread creates a new outer object but copies the nested reference in the copy question. A mutation through that shared reference reaches the same nested object. Assigning a new outer label only changes the copied object's property. Draw two outer boxes pointing to one nested box before trying the follow-up that copies another level.

Map's object keys also depend on reference identity. A fresh object with matching fields is a different key. If an algorithm means to group entries by an ID, choose that primitive ID as the key explicitly. The [TypeScript collections guide](/guides/typescript-collections) discusses these runtime rules alongside missing-value and readonly contracts; its TypeScript annotations do not change object identity.

Defaulting expressions require their own contract. Destructuring uses its default when a value is undefined. Logical OR selects its fallback for any falsy left operand. Nullish coalescing selects its fallback for null or undefined. A count of zero and an explicitly supplied null can therefore behave differently even when several expressions are described casually as defaults.
