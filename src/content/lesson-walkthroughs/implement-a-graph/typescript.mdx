The lesson implements a graph as an adjacency list. Each vertex's unique data value identifies a key, and its entry stores neighboring vertices. The constructor chooses directed or undirected behavior, defaulting to undirected. This makes edge insertion and vertex removal concrete without requiring a separate object for every possible pair of vertices.

## Establish vertices before connecting them

Adding a vertex creates an empty neighbor collection. A newly created isolated vertex still belongs to the graph even though it has no edges. Decide what repeated insertion of the same key should do; blindly replacing an existing neighbor collection would erase connections.

Adding an edge updates the source vertex's neighbors. In an undirected graph it must also update the reverse relationship. That symmetry is an invariant to check after every mutation. A directed graph adds only the requested direction. The choice affects reachability, so a traversal cannot infer the reverse edge unless it is actually stored or guaranteed by the model.

## Remove incoming references as well as the vertex

Deleting a vertex's own entry does not remove references to it from other adjacency lists. The removal operation must also delete those incoming edges. In an undirected graph, affected neighbors contain the reverse entries. In a directed graph, incoming edges may originate anywhere unless another index records them.

Test a vertex with several neighbors, an isolated vertex, a self-loop if permitted, and a missing vertex. Decide whether repeated edges are allowed or whether neighbor collections represent sets. Arrays and sets provide different duplicate behavior and removal costs, so the API should choose deliberately.

## Analyze operations using the stored collections

An adjacency list occupies O(V + E) storage, counting an undirected edge in both endpoint lists. Adding a neighbor can be direct, while checking uniqueness or removing it from an array may require a scan. Removing a vertex may inspect many neighbor collections; it is not automatically constant time because a top-level key deletion is quick.

A traversal should visit the structure left by its actual mutations, including isolated vertices when the task asks for complete coverage.

## Follow a directed and an undirected edge

Create vertices A, B, and C. In directed mode, adding A → B stores B in A's adjacency list only. In undirected mode, it also stores A in B's list. Removing B deletes its own list and filters B from every remaining list, including incoming directed edges.

This implementation stores adjacency entries in lists, so duplicate edges are preserved. In undirected mode, adding a self-loop appends twice to the same list. Those are consequences of the shown representation, not a claim that every graph API chooses the same policies.

## Establish preconditions before mutation

Add each vertex once before adding edges. Calling addVertex again replaces that vertex's existing adjacency list in these teaching versions. Some languages also create or tolerate missing endpoint entries differently, so missing vertices are outside the shared cross-language contract. A product API should choose and enforce one policy explicitly.

With ordinary map assumptions, adding a vertex and appending an edge have expected or amortized constant structural cost. Removing a vertex scans remaining adjacency lists, for O(V + E) work. Storage is O(V + E), counting every stored adjacency entry. Tests include directed edges, reciprocal edges, repeated edges, self-loops, and removal of a vertex with both incoming and outgoing edges. Compare adjacency counts by vertex rather than relying on hash-map iteration order.

## TypeScript example and implementation choices

The string index signature describes adjacency lists but does not guarantee a requested endpoint exists. addEdge assumes both vertices were added first, and addVertex resets an existing entry. Those runtime preconditions remain necessary despite the types. The original object-backed structure is suitable for the lesson's named vertices; Map would give a clearer arbitrary-string-key boundary for a reusable graph API.

### Complete implementation

```typescript
interface AdjacencyList {
  [node: string]: string[];
}

class Graph {
  adjacencyList: AdjacencyList;
  undirected: boolean;


  constructor(undirected: boolean = true) {
    this.adjacencyList = {};
    this.undirected = undirected;
  }

  addVertex(vertex: string): void  {
    this.adjacencyList[vertex] = [];
  }

  addEdge(source: string, destination: string): void {
    this.adjacencyList[source].push(destination);

    if (this.undirected) {
      this.adjacencyList[destination].push(source);
    }
  }

  removeVertex(vertex: string): void {
    delete this.adjacencyList[vertex];

    Object.keys(this.adjacencyList).forEach(node => {
      this.adjacencyList[node] = this.adjacencyList[node].filter(v => v !== vertex);
    });
  }
}
```
