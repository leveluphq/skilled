An array puts an ordered sequence behind numeric indexes. The useful question in an interview is which operations can reach an element directly and which must move other elements. The recording introduces that distinction, then uses capacity and resizing to explain why a dynamic array can grow without making every append expensive.

## Trace an insertion before naming its cost

Start with `[10, 20, 30, 40]`. Reading index 2 gives 30 without scanning the preceding values. Inserting 15 at index 1 changes the positions of 20, 30, and 40. Those shifts explain the linear work. Removing index 1 closes the same gap in the other direction. Finding the value 30 is a separate operation from reading a known index: an unsorted array may need a scan to find it.

Appending leaves existing indexes alone when spare capacity is available. A dynamic array occasionally allocates more storage and copies its elements. With geometric capacity growth, those copies add up to linear work over a long sequence of appends, giving amortized constant time per append. A single append that triggers a resize can still take linear time.

## Keep the representation assumptions visible

The contiguous, fixed-width array model gives a useful explanation for direct indexed access. A JavaScript array has additional language behavior, including holes and object properties, so that model does not describe every JavaScript array implementation detail. Use the model to reason about the exercise, and distinguish it from promises made by a particular runtime.

An element's size and the complete array allocation are different quantities. Twenty Java integers require 80 bytes for their values; an actual array object has additional overhead. Changing the operating system does not change the Java integer's specified width.

## Follow one insertion through the example

Start with `[4, 8, 12]`, an insertion index of `1`, and a new value of `6`. The result should be `[4, 6, 8, 12]`. The prefix before index 1 stays in place. The original suffix moves one position right. The example constructs a separate result, so the caller still owns an unchanged three-element input after the function returns.

Its contract accepts positions from zero through the input length, including insertion after the last element. That differs from the course's small map-backed DynamicArray, whose `insert` method accepts existing positions only. Use `push` to append in that implementation. A shared operation name does not guarantee identical boundary behavior.

## Count copying and check the boundaries

Copying the input and making room for the new value costs O(n) time and O(n) returned storage. An insertion at the beginning moves the largest suffix; an insertion at the end still copies the input in this particular function. Neither case is constant time merely because an array index is involved.

Test an empty input, both endpoints, repeated values, and negative numbers. Check the original array afterward as well as the returned value. ## Python example and implementation choices

list.copy creates the independent outer list used for insertion. Python's list.insert tolerates some out-of-range positions, but the cross-language example accepts only positions from zero through len(values). Keeping that precondition avoids teaching Python's clamping behavior as a universal array rule. The elements are integers here; copying a list of mutable objects would still share those objects.

### Worked example

```python
def arrays_insert(values: list[int], index: int, item: int) -> list[int]:
    copy = values.copy()
    copy.insert(index, item)
    return copy
```
