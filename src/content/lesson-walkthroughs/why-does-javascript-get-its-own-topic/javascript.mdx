## Connect behavior to an observable result

A language question becomes easier to reason about when you specify the result. For a callback, identify when it executes and which values it can read then. For a method, identify the call form and receiver. For an asynchronous wrapper, write a timeline of calls and settlements before proposing an implementation.

The [Fix this lesson](/watch/fix-this) has two independent failures: a method loses its intended receiver, and callbacks share a function-scoped loop variable. Both can produce incorrect output even when the underlying array traversal is straightforward. Explaining each failure separately is more useful than labeling the whole example a JavaScript quirk.

## Choose the abstraction that matches the contract

[Array Methods](/watch/array-methods) asks you to replace loops according to their purpose: transformation, selection, membership, or a quantified predicate. [Pub-Sub](/watch/pub-sub-and-event-driven-programming) stores callbacks by event name and then manages their lifetime. These exercises also have algorithmic costs. Publishing to many listeners requires visiting them. Copying arrays allocates storage. A callback that captures a large object can retain it for as long as the callback remains reachable. Language semantics and resource analysis belong in the same explanation.

## Validate a runtime value at a boundary

The example accepts an unknown value and returns a finite score between zero and one hundred, or null. The number 8 passes; the string `"8"` does not. Zero is valid. NaN, infinity, negative values, and values above one hundred are rejected.

This is a small model for handling JSON, form input, or another runtime boundary. TypeScript can describe the value after checking it, but it cannot make a string arriving over a network become a number. A type assertion alone would not validate or convert that data.

## Keep conversion separate from acceptance

If a product should accept numeric strings, add an explicit parsing contract. Decide what an empty string means, whether whitespace is allowed, and whether partial strings such as `8points` should pass. Calling a conversion function without stating those choices can accidentally accept inputs that the interface meant to reject.

The function performs a fixed number of checks and uses O(1) time and storage for its number/primitive contract. That simplicity makes the behavior easy to enumerate. Test zero, both range endpoints, a decimal, a numeric string, null, an object, NaN, and infinity. TypeScript's `unknown` parameter forces the implementation to narrow before arithmetic; the JavaScript version relies on the same executable checks. Both have the same runtime acceptance policy.

## JavaScript example and implementation choices

The typeof check rejects objects, strings, and null before the range comparisons. Number.isFinite avoids coercing numeric-looking strings, unlike some older global numeric helpers. Returning null keeps a valid zero distinguishable from failure. This function validates an already numeric score; parsing a form string would require an explicit conversion step and decisions about whitespace, decimal syntax, and invalid text.

### Worked example

```javascript
function parseScore(value) {
    if (typeof value !== 'number' || !Number.isFinite(value))
        return null;
    if (value < 0 || value > 100)
        return null;
    return value;
}
```
