Binary search finds a target by repeatedly discarding a portion of a sorted search space. Its central requirement is a rule that makes one portion impossible. The recording contrasts searching methods and then follows the midpoint decisions. A correct implementation needs both that exclusion argument and boundary updates that always make progress.

## Choose one interval convention

With an inclusive interval, low and high both identify candidates. The interval is empty when low passes high. A midpoint match can return immediately for an ordinary exact-match contract. Otherwise, move a boundary beyond the midpoint because that position has already been ruled out.

For `[2, 5, 8, 11, 14]` and target 11, the first midpoint contains 8. Sorted order proves that 8 and every earlier value are too small. The remaining candidates are 11 and 14. That proof depends on ordering; applying the same updates to an unsorted array would discard possible answers.

## Decide what duplicates mean

Finding any matching position, the first matching position, and the insertion boundary are different tasks. Returning at the first equality does not establish that a match is the first one. Boundary-search variants often keep a match as a candidate and continue on one side. State the requested result before translating the general idea into code.

Check an empty array, one item, two items, a missing target, and a target at either end. Two-item intervals are particularly useful for catching a boundary that fails to move. In a fixed-width language, calculating the midpoint from the distance between boundaries can avoid overflowing their sum.

## Count comparisons and representation costs

Under bounded-cost comparisons and direct indexed access, each step halves the candidate count, giving logarithmic time. The iterative version needs constant auxiliary storage. A linked list does not offer the same direct midpoint access; reaching a midpoint can require traversal, changing the cost model.

## Search for the first occurrence

For the sorted input `[1, 3, 3, 3, 8]` and target 3, the example returns index 1. It computes a lower bound using a half-open interval `[low, high)`. Values before low are known to be too small. Values at or after high are outside the remaining candidates for the first position that could hold the target.

When the middle value is smaller than the target, low becomes middle + 1. Otherwise high becomes middle, keeping a matching middle value available while looking farther left. On termination low equals high. One final equality check distinguishes an actual match from an insertion position.

## Test interval edges and duplicate values

An empty input begins with both bounds at zero and returns −1 after the final guard. A target above every element produces an insertion position equal to the length, so indexing before checking that bound would be an error. Targets below the first element and repeated targets exercise the opposite boundary.

The function assumes the values are already sorted in ascending order. Sorting inside a wrapper changes both its cost and the meaning of the returned index. The search itself uses O(log n) comparisons and O(1) additional storage for random-access input. If you use a linked structure instead, reaching the middle is no longer a constant-time indexing operation. Keep that representation cost in the explanation.

## C# example and implementation choices

`List<int>` supplies constant-time indexed reads, and the method keeps the input unchanged. high is an excluded upper bound, which handles an empty list naturally. Equality moves high left during the search, so the returned match is the earliest duplicate. A final equality check is still necessary because lower-bound search can locate a valid insertion position for a missing target.

### Worked example

```csharp
using System;
using System.Collections.Generic;

public static class BinarySearchExample {
public static int BinarySearch(List<int> values, int target) {
    int low = 0, high = values.Count;
    while (low < high) {
        int middle = low + (high - low) / 2;
        if (values[middle] < target) low = middle + 1;
        else high = middle;
    }
    return low < values.Count && values[low] == target ? low : -1;
}
}
```
